Still **not** in the database, each deliberately:

- `audit_log` yearly partitioning — unscheduled; it forces a composite `(id, createdAt)` primary key and v1 volume does not need it.
- Rules that need a count or another table: a line cannot deactivate with `ACTIVE` accounts; `TALLIED` requires every handover acknowledged; a Senior approves only on their own line. These live in the services that own them.
- `outstandingAmount = accountAmount − collectedAmount` and `capturedAt ≤ syncedAt` — the first is a cache reconciled nightly, the second would reject genuine offline records from a device with a fast clock.
- Which `status` transitions a collection may make — unspecified, so any transition is allowed; only the other columns are frozen.

**If `collection.varianceTolerance` (BR-08) is ever built, `collection_classification_check` must be relaxed in the same change** — classification stops being a pure function of the row.

**How the constraints coexist with Prisma.** Partial unique indexes are declared in `schema.prisma` through the `partialIndexes` preview feature, so Prisma owns them. CHECKs, triggers and `NULLS NOT DISTINCT` cannot be expressed there; they live in the `constraints_*` migrations, and Prisma neither diffs nor drops them — `prisma migrate diff` from the live database to the schema was verified empty after all nine migrations applied. Every trigger function pins `SET search_path FROM CURRENT`, because the runtime client does not set `search_path`. Trigger errors keep plpgsql's default SQLSTATE or `check_violation`: Prisma's pg adapter reports `restrict_violation` as "Foreign key constraint violated on the (not available)" and drops the message.

**"Transaction-rollback isolation" is delivered in two tiers, because it cannot be delivered as one.** A supertest request crosses a socket into a different async context, so the HTTP handler uses the application's Prisma client rather than the test's transaction-bound one, and no `AsyncLocalStorage` bridges that.

- **Tier 1 — service, repository and constraint tests** get true per-test rollback through `withRollback`. It runs `SET CONSTRAINTS ALL IMMEDIATE` before rolling back, which is the only reason a test of a deferred trigger can fail.
- **Tier 2 — HTTP tests** write for real. Every identifying value they create carries the run's `testRunTag` (use `testEmail()`), and `deleteTestRunData` removes exactly those rows. A Tier 2 test that creates domain rows must extend that function with a tagged delete per table — never a bulk delete. **Append-only tables cannot be cleaned up** — `collection`, `ledger_transaction`, `ledger_entry` and `audit_log` reject DELETE — so a Tier 2 test must never write them: prove those writes in Tier 1, and route incidental writes elsewhere (HTTP tests record sign-in audit attempts in memory through `test/app.ts`).

**The suite does not apply migrations.** Global setup runs `prisma migrate status` and fails with an instruction to run `pnpm --filter @repo/db db:deploy`, so running tests never changes the development database's structure as a side effect.

**`?schema=` does not set `search_path` under Prisma 7.** It is a Prisma-specific query parameter: the CLI parses it, but `pg` silently ignores unknown parameters. `@repo/db` parses it and passes it to the adapter explicitly, which qualifies generated queries but still leaves `current_schema()` untouched — so **raw SQL and trigger functions must not rely on `search_path`**.

`DATABASE_URL` is set at **vitest config scope** in the e2e config, not in a setup file. Config is evaluated in the parent process before workers fork, and workers inherit the environment; `test.env` is applied too late for a module that reads the variable while importing.

> The RBAC test harness is a story, not a chore. It generates a test per matrix cell, so a new endpoint without matrix entries fails the suite — which is what makes release gate 5 real rather than aspirational.

**The seed dataset** is the only dataset anyone will see before launch, so it carries the awkward cases deliberately — uneven final instalment, overdue account, two concurrent accounts, mid-account line transfer, cash discrepancy, approved correction. Sized L rather than S because generating a month of plausible collection history across 250 accounts, with realistic low/extra/missed distribution, is real work — and a seed of perfect happy-path data would be worth very little.

## Keeping this current

When a story is finished, in the same pass:

1. **Set its `State` here to `Done`.** A story half-built is `WIP`, with the remaining part named in the row if it is not obvious.
2. **Update the progress counts** at the top of this file.
3. **If a package, database or piece of infrastructure now exists**, remove it from the gap table in [`project-structure.md`](../04-engineering/project-structure.md#not-yet-present) and add it to the workspace tree there.
4. **If behaviour ended up different from the spec**, fix the module spec in `01-product/modules/` — the spec is wrong, not the code, once the code ships. A decision that is hard to reverse also gets an [ADR](../02-architecture/adr/).
5. **At a phase boundary only**, update the phase marker in [`roadmap.md`](roadmap.md) and the implementation table in [`../README.md`](../README.md). Those are coarse summaries; per-story state lives here and nowhere else.

Do not record status in two places. If another document needs to state progress, it links here.

## Where the weight sits

**Phase 3 holds the only XL item in the project** — the IndexedDB outbox — alongside four L items, with every story in it P0 except three. A third of the technical risk is concentrated in one phase, and it is the phase whose failure mode is invisible until a Junior loses a route's worth of collections.

Phases 1 and 2 carry the rest of the P0 weight. Phase 5 has no P0 stories at all.

**If the schedule slips**, compress Phase 5. Dashboards are how the business _sees_ the data, and they can ship incrementally after launch.

**Do not compress Phase 3.** A partial offline implementation is worse than none, because it will appear to work right up until the day it silently loses a route's worth of collections — and by then it is trusted.
